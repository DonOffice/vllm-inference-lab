## 2. 日常操作:启动 / 验证 / 停止服务

```bash
# 启动 vLLM OpenAI 兼容服务(后台跑,日志落盘)
conda activate vllm
# 注:VLLM_USE_FLASHINFER_SAMPLER=0 是本机必要的(缺 flashinfer-cubin 时
#     采样算子会去找 nvcc 而失败;关掉后走 Triton 采样,性能几乎无差)
VLLM_USE_FLASHINFER_SAMPLER=0 nohup vllm serve ~/models/Qwen3-1.7B \
  --served-model-name qwen3-1.7b \
  --max-model-len 8192 --gpu-memory-utilization 0.9 \
  > ~/bench/server.log 2>&1 &

# 等待就绪(日志出现 "Application startup complete" 即可,1.7B约1分钟,8B约1.5分钟)
tail -f ~/bench/server.log

# 验证(OpenAI 兼容接口)
curl http://127.0.0.1:8000/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "qwen3-1.7b",
  "messages": [{"role": "user", "content": "你好,介绍一下你自己"}],
  "max_tokens": 64
}'

# 查看服务进程 / 停止
pgrep -af "vllm serve"     # 找 PID
kill <PID>                 # 停止(推荐按 PID 杀)
# 坑:pkill -f "vllm serve" 会匹配到你当前 shell 里刚敲过的同款文本,
#     连自己终端一起杀;要么用 pkill -f "[v]llm serve" 字符类写法,要么按 PID 杀。
```

常用启动参数(完整清单 `vllm serve --help=all`):

| 参数 | 作用 | 本机建议值 |
|---|---|---|
| `--max-model-len` | 单请求最大上下文 | 8192(16GB 显存别开太大) |
| `--gpu-memory-utilization` | 允许 vLLM 用的显存比例 | 0.90(留 1.6G 给系统/显示) |
| `--enable-prefix-caching` / `--no-enable-prefix-caching` | 前缀缓存开关 | 默认开;对照实验时关 |
| `--max-num-seqs` | 并发批次上限 | 256 默认即可,压测时可调小观察批效应 |
| `--served-model-name` | API 里的 model 名 | 起短名,省得写长路径 |

## 3. 吞吐与延迟怎么看(三层方法论)

### 3.1 先懂指标:测 LLM 到底测什么

| 指标 | 含义 | 什么时候重要 |
|---|---|---|
| **TTFT** (Time To First Token) | 从发请求到收到第 1 个 token 的时间 | 由 prefill(预填充)决定,长 prompt/高并发时恶化,交互体验的关键 |
| **TPOT/ITL** (Time Per Output Token) | 生成阶段平均每个 token 的间隔 | 由 decode(解码)决定,带宽瓶颈,单流速度就是它的倒数 |
| **Throughput** (tok/s) | 全系统每秒吐出的 token 总量 | 并发越高越大(批处理摊薄了权重读取),看的是"总产能" |
| **Goodput** | 按请求级 SLA(如 TPOT<100ms)过滤后的吞吐 | 生产容量规划用 |

**核心直觉**(本机数字):4070 Ti Super 显存带宽 672GB/s。Qwen3-8B INT4 权重约 5GB,纯 decode 每 token 至少要把权重读一遍 → 单流理论上限 ≈ 672/5 ≈ 134 tok/s,实测打 5~7 折(激活/注意力/KV 也要读写)。**并发为什么能提总吞吐**:批处理时 16 个请求共享一次权重读取,带宽利用率大增,但每个请求自身的 TPOT 会变差。这就是所有压测数字背后的物理意义。

### 3.2 实时观察:工具层

```bash
# GPU 状态(nvitop 交互式,类似 htop;gpustat 一行速览)
nvitop          # conda 环境里已装

grep -E "Engine.*throughput|prefix cache" ~/bench/server.log | tail -5
```

### 3.3 系统性压测:官方工具

```bash
conda activate vllm

# ① 离线纯吞吐(bs=1 单流 + bs=N 批量,衡量"机器极限")
vllm bench throughput --model ~/models/Qwen3-8B-GPTQ-Int4 \
  --input-len 512 --output-len 256 --batch-size 1

# ② 在线服务压测(模拟真实到达,产出 TTFT/TPOT/吞吐 + 百分位)
#    固定并发档位:--request-rate inf + --max-concurrency N
#    ⚠ 两个已验证的坑:
#      a) --base-url 不要带 /v1 后缀(工具自己拼),带了解析到 /v1/v1/... 会全 404;
#      b) --model 传服务名时必须配 --tokenizer <本地模型路径>,否则它去 huggingface.co
#         拉 tokenizer,国内直接超时。
vllm bench serve --backend openai --base-url http://127.0.0.1:8000 \
  --model qwen3-8b-awq --tokenizer ~/models/Qwen3-8B-AWQ \
  --dataset-name random --random-input-len 1024 --random-output-len 256 \
  --num-prompts 32 --request-rate inf --max-concurrency 4 \
  --percentile-metrics ttft,tpot,itl \
  --save-result --result-dir ~/bench/results --result-prefix conc4

# ③ 单批延迟细拆(⚠ 这是离线测试,会自己拉起引擎 —— 必须先停掉占用 GPU 的服务!)
vllm bench latency --model ~/models/Qwen3-8B-AWQ --input-len 512 --output-len 128

# ③ 单批延迟细拆(注入延迟是多少、decode 每步多少)
vllm bench latency --model ~/models/Qwen3-8B-GPTQ-Int4 --input-len 512 --output-len 128
```

**`vllm bench serve` 的数据集选择**:`random`(可控输入输出长度,做容量规划)、`sharegpt`(真实对话分布)、`prefix-repetition`(专门测前缀缓存!)。加 `--save-result --result-dir x --label y` 可以把结果存下来对比(0.32 里叫 `--label`,没有 `--result-prefix`)。

> **⚠ 实测踩坑:固定种子 × prefix caching 会污染对比数据**。bench 默认随机种子固定
> (每次生成同一批 prompt),而服务默认开前缀缓存 → 第二次压测会命中第一次留下的 KV,
> TTFT 假性偏低(实测 c=2 的 TTFT 从 236ms 掉到 35ms)。**对比实验时:每档用不同
> `--seed`,或档间重启服务清缓存**,否则 TTFT 不可信(吞吐/TPOT 不受影响)。

### 3.4 SGLang 侧怎么看

```bash
conda activate sglang
# ⚠ 必须带这三行:本机没装系统级 CUDA 工具链,nvcc 来自共享的 cudatoolkit 环境;
#   flashinfer 首次启动要 JIT 编译内核,需要 CUDA_HOME + LIBRARY_PATH(后者补上
#   libcuda/libcudart 的链接符号,WSL 透传目录里只有 .so.1 没有开发符号)。
#   编译结果缓存在 ~/.cache/sglang/.cache/flashinfer,之后启动不再编译。
export CUDA_HOME=$HOME/miniconda3/envs/cudatoolkit
export PATH=$CUDA_HOME/bin:$PATH
export LIBRARY_PATH=$HOME/cuda-libs:$CUDA_HOME/lib:$LIBRARY_PATH

# 启动(python -m 方式,参数体系与 vLLM 不同;默认端口 30000)
python -m sglang.launch_server --model-path ~/models/Qwen3-1.7B \
  --host 127.0.0.1 --port 30000 --mem-fraction-static 0.85 --context-length 8192
# 就绪标志(日志):"The server is fired up and ready to roll"

# 压测(⚠ SGLang 0.5.22 自带 bench 有个坑:即使 --dataset-name random 也会去
#   huggingface.co 拉 ShareGPT 文件,国内不可达。推荐直接用 vLLM 的压测客户端打
#   SGLang 的端口 —— 同一客户端同一负载,跨框架对比反而更公平:)
~/miniconda3/envs/vllm/bin/vllm bench serve --backend openai \
  --base-url http://127.0.0.1:30000 --model default --tokenizer ~/models/Qwen3-1.7B \
  --dataset-name random --random-input-len 1024 --random-output-len 128 \
  --num-prompts 16 --request-rate inf --max-concurrency 4 --seed 42
# (SGLang 的模型名固定是 "default";实测 1.7B@c4:374.9 tok/s,TTFT 171ms,TPOT 9.3ms)

# sglang 也有 /metrics 和 /get_server_info
curl -s http://127.0.0.1:30000/get_server_info | python -m json.tool | head -30
```

## 4. 源码开发工作流(改 Python 立即生效)

### 4.1 原理:为什么改 Python 能"立即生效"

vLLM = Python 调度/服务代码 + C++/CUDA 编译内核。我们用 `VLLM_USE_PRECOMPILED=1`
做的可编辑安装(`pip install -e .`)只把**编译产物**从官方 nightly wheel 里借来,
**Python 代码则直接指向 ~/dev/vllm 源码树**。于是:

- 改 `~/dev/vllm/vllm/**.py` → **重启服务即生效**(python -e 路径优先)
- 改 `csrc/**`(C++/CUDA)→ 需要重新编译 → 本机没装 CUDA 工具链,不做(见 4.4)

```bash
# vllm-dev 环境里验证"改代码生效":
python -c "import vllm; print(vllm.__file__"
# 应打印 /home/sikai/dev/vllm/vllm/__init__.py ← 指向源码树,而不是 site-packages
```

### 4.2 开发循环示例(以加一行日志为例)

```bash
conda activate vllm-dev   # 注意!开发用这个环境,不是 vllm
```

### 4.4 改 C++/CUDA 内核怎么办

本机没装完整 CUDA 工具链(WSL 内装 nvcc 属于可选项,不算显卡驱动,但占几个 GB)。
路线上有两条:① `VLLM_USE_PRECOMPILED=0` 完整源码编译(需要装 cuda-toolkit,约
30-60 分钟);② 内核实验优先通过 **Triton**(纯 Python 写 GPU 内核,vLLM/SGLang 大量
使用,`vllm/attention/triton_backend/` 有现成例子)——学习期推荐后者,零编译开销。

## 5. Bug 复现方法论(从 GitHub issue 到本机复现)

**标准流程**(以学习为目的,建议每周练一个):

1. **挑 issue**:vLLM 仓库 → Issues → 筛 `label:bug` + 未关闭,找带复现脚本的。
2. **锁版本**:issue 里通常说 "v0.31.0 regression" → `cd ~/dev/vllm && git fetch --tags && git checkout v0.31.0`
   (浅克隆下 `git fetch --unshallow` 可补全历史,用于 `git bisect`)
3. **最小化**:把 issue 的复现脚本砍到最短(短 prompt、小模型、去掉无关参数)。
4. **复现**:在 vllm-dev 环境跑;若 issue 出在 nightly,先 `pip install -U vllm --pre` 对齐。
5. **定位**:按调用链 `API server → scheduler → worker → 内核` 二分插桩(加 print/断点)。
6. **验证修复**:改代码确认修好 → 去 PR 页看官方是怎么修的 → 对比自己的思路。

**二分找回归**:
```bash
cd ~/dev/vllm && git fetch --unshallow        # bisect 需要完整历史(约 1GB)
git bisect start HEAD v0.30.0                 # 在"坏"和"好"之间二分
# 每步:重建?不用——VLLM_USE_PRECOMPILED=1 pip install -e . 只借内核,Python 端秒切
git bisect run bash -c "python repro_script.py && exit 1 || exit 0"
```

## 6. Prefix Caching 实验速查(原理 + 怎么做)

**原理**:多轮对话里,第 N 轮的 prompt = system + 前 N-1 轮历史,前缀重复。
vLLM 把 KV cache 按 16-token 块哈希存储;命中块直接复用 KV,**prefill 不用重算**,
TTFT 大幅下降(还能省显存:LRU 逐出旧块)。

```bash
# 对照实验(完整脚本见 ~/bench/multiturn_prefix.py)
# A组:缓存开(默认)        → vllm serve ...(不加参数)
# B组:缓存关              → vllm serve ... --no-enable-prefix-caching
python ~/bench/multiturn_prefix.py --base-url http://127.0.0.1:8000 \
  --model qwen3-1.7b --rounds 3 --turns 6

# 官方工具交叉验证(专用数据集):
vllm bench serve --backend vllm-openai ... --dataset-name prefix-repetition \
  --prefix-length 2048 --num-prompts 32
```

**证据三件套**:① 开/关两组每轮 TTFT 曲线;② `/metrics` 里 `vllm:prefix_cache_queries_hits_total` 计数差;③ server.log 中 `Prefix cache hit rate` 行。

## 8. 建议学习路径

1. **跑通并发压测,亲手看到数字**(基线数据怎么随并发变化)→ 建立物理直觉
2. **prefix caching 实验** → 理解 KV cache 是 vLLM 一切设计的中心
3. **读离线推理入口** `vllm/entrypoints/llm.py` → `vllm/v1/engine/processor.py` → `scheduler.py`
   (边读边在 vllm-dev 环境加 print 观察一条请求的生命周期)
4. **对照 SGLang**:同模型两边各压一遍,数字差异本身就是最好的深入线索
5. **挑一个 bug 练复现**(第 5 节流程)
