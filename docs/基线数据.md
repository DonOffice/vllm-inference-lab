# Qwen3-8B-AWQ 基线性能数据(RTX 4070 Ti Super 16GB)

> 日期:2026-10-27 | vLLM 0.32.0 wheel 版 | 量化:auto AWQ-INT4 → **Marlin 内核**(启动日志确认)
> 服务参数:`--max-model-len 8192 --gpu-memory-utilization 0.9`,prefix caching 默认开(本测试负载无共享前缀,不影响)
> 采样路径:Triton(`VLLM_USE_FLASHINFER_SAMPLER=0`,见环境报告 2.1)
> 原始数据:WSL `~/bench/results/clean*-20261027-*.json` | 工具:`vllm bench serve`(随机数据集)

## 1. 主结果:单流 + 4 档并发

负载:每请求输入 1024 token、输出 256 token,每档 32 个请求,固定并发(`--request-rate inf --max-concurrency N`),每档独立随机种子(避免缓存污染,见 §3)。

| 并发 | 请求吞吐 (req/s) | **输出吞吐 (tok/s)** | TTFT 均值 (ms) | TTFT 中位 (ms) | TTFT P99 (ms) | TPOT 均值 (ms) | 单流速度 (tok/s/流) |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.28 | **71.7** | 278 | 276 | 307 | 12.9 | **77.5** |
| 2 | 0.48 | 122.9 | 449 | 450 | 622 | 14.6 | 68.6 |
| 4 | 0.82 | 209.6 | 737 | 856 | 1214 | 16.3 | 61.5 |
| 8 | 1.25 | 320.5 | 1307 | 1412 | 2354 | 19.9 | 50.3 |

*(单流速度 = 1000/TPOT,即每条请求自身的生成速度;总吞吐 = 单流速度 × 并发数)*

## 2. 数字怎么读(物理直觉)

1. **单流 77.5 tok/s**:decode 阶段每个 token 都要把 5.6GB 的 INT4 权重从显存读一遍,
   理论上限 = 672GB/s ÷ 5.6GB ≈ 120 tok/s,实测 77.5 = **65% 带宽利用率**
   (KV cache 读写、激活、采样、Python 开销占掉其余)。落在 40~90 tok/s 的合理区间,
   ✅ 合理性校验通过:量化确实生效(Marlin),计算在 GPU 上,没有被 CPU/PCIe 拖累。
   *(原验收提示按 8GB 权重估的上限是 84 tok/s;AWQ 比 FP8/GPTQ 更小,上限相应更高。)*
2. **总吞吐随并发上升(71.7 → 320.5)**:批处理让多条请求**共享一次权重读取**——
   这就是连续批处理(continuous batching)的本质:并发 8 时每 token 的有效带宽需求降到 1/8。
3. **单流速度随并发下降(77.5 → 50.3)**:批越大,每步要算的 attention/KV 越多,
   加上调度开销——**吞吐和延迟是买方市场,加并发是在拿单流延迟换总产能**。
4. **TTFT 随并发恶化(278ms → 1.3s)**:排队 + prefill 与 decode 混排(chunked prefill)。
   交互式服务想保 TTFT,就要限制并发或提高 `--max-num-batched-tokens` 预算。

## 3. 方法论注记:为什么跑了两次(重要的坑)

第一轮 sweep 的 c=2/4/8 档 TTFT 异常低(c=2 仅 35ms,< c=1 的 276ms,物理上不可能)。
**根因**:`vllm bench serve` 默认固定随机种子 → 四档压测使用**同一批 prompt**;服务默认开
prefix caching → 后跑的档位命中了前面档位留在 KV cache 里的前缀,prefill 被跳过。
**修正**:重启服务清空缓存 + 每档独立 `--seed`。上表即修正后的干净数据。

附带观察:污染版 c=8 总吞吐 445 tok/s vs 干净版 320 tok/s——差值本身就是
"前缀命中对吞吐的增益"的量化体现(约 +39%),与《实验报告》的 TTFT 结论互相印证。

## 4. 复现命令

```bash
conda activate vllm
# 1) 起服务(参数同上,日志 ~/bench/qwen3-8b-final2.log)
VLLM_USE_FLASHINFER_SAMPLER=0 nohup vllm serve ~/models/Qwen3-8B-AWQ \
  --served-model-name qwen3-8b-awq --max-model-len 8192 --gpu-memory-utilization 0.9 \
  > ~/bench/server.log 2>&1 &

# 2) 压测(每档换 --seed!)
vllm bench serve --backend openai --base-url http://127.0.0.1:8000 \
  --model qwen3-8b-awq --tokenizer ~/models/Qwen3-8B-AWQ \
  --dataset-name random --random-input-len 1024 --random-output-len 256 \
  --num-prompts 32 --request-rate inf --max-concurrency 8 --seed 136 \
  --percentile-metrics ttft,tpot,itl \
  --save-result --result-dir ~/bench/results --label clean8
```

## 6. 勘误附注(2026-10-31):本报告数字含"冷启动税"

本文所有数字采集于 10-27,服务就绪后未预热直接开压。10-31 同参数复测(先跑 8 条预热请求)显示本表系统性偏低 **26-33%**:c=1 71.7→90.6、c=8 320.5→426.4 tok/s。差额是首批请求替 torch.compile / CUDA-graph / 时钟爬升买的单。本表保留作历史记录;**对外引用请用 [SGLang-vs-vLLM横评](SGLang-vs-vLLM横评.md) 的预热后数字**,并遵守三条压测军规:每档独立 seed、先预热、隔天数据不直接 A/B。
