# Prefix Caching 开/关对照实验报告

> 日期:2026-10-27 | 模型:Qwen3-8B-AWQ(INT4, Marlin 内核) | 硬件:RTX 4070 Ti Super 16GB
> vLLM 0.32.0(V1 引擎,wheel 环境) | 服务参数:`--max-model-len 8192 --gpu-memory-utilization 0.9`

## 1. 实验目的与原理

**Prefix caching(前缀缓存)原理**:vLLM 把 KV cache 按 16-token 块组织,每个块的哈希
由"内容 + 前缀块哈希"链式构成。多轮对话中,第 N 轮请求的 prompt = system prompt +
前 N-1 轮完整历史,**前缀部分与之前请求完全一致** → 其 KV 块可直接复用,
prefill(预填充)只需计算新增的最后几十个 token。

**收益**:TTFT(首 token 延迟)大幅下降 + 省显存/带宽(不重算不重写)。
**代价**:哈希查询开销、缓存逐出(LRU)管理;对无重复前缀的负载收益为零。

## 2. 实验设计

- **负载**:多轮对话,`system prompt` 约 6000 token(48 段固定背景资料),
  6 轮对话(每轮问一句,历史逐轮累积),3 个重复会话取稳态。
  脚本:`bench/multiturn_prefix.py`(asyncio 流式请求,TTFT = 发出请求到首个内容增量)。
- **三组对照**:
  | 组 | 服务配置 | 负载 | 预期 |
  |---|---|---|---|
  | ON-hit | 缓存开(默认) | 共享长 system prompt | 首条冷,后续秒回 |
  | ON-miss | 缓存开 | 每轮换随机内容的同长 system prompt | 永不命中,≈关缓存 |
  | OFF | `--no-enable-prefix-caching` | 同 ON-hit | 每轮全量 prefill |
- ON-miss 组同时是方法学校验:它与 OFF 组数字应当一致(都做全量 prefill),
  互相印证实验有效性。

## 3. 结果(每轮 TTFT,毫秒)

### ON-hit(缓存开 + 共享前缀)—— 最终一轮数据

| 轮次 | 冷会话(第1个) | 热会话(第2/3个,中位数) |
|---|---|---|
| turn 1 | **1081.8** | 27.1 |
| turn 2 | 33.5 | 27.0 |
| turn 3 | 30.9 | 27.4 |
| turn 4 | 34.7 | 28.3 |
| turn 5 | 58.0 | 28.3 |
| turn 6 | 32.8 | 28.8 |

### ON-miss(缓存开 + 随机前缀,永不命中)

冷会话:1060.0 / 1088.7 / 1069.3 / 1090.6 / 1110.4 / 1112.9;热会话中位数 1044.9~1091.4
→ 每轮都 ~1050-1110ms,和轮次无关。

### OFF(缓存关)

冷会话:1259.3 / 1002.1 / 988.9 / 976.7 / 997.1 / 1008.4;热会话中位数 966.1~1010.1
→ 每轮都 ~1000ms 上下,和轮次无关。

### 核心对比

| 指标 | 缓存 ON(热) | 缓存 OFF | 差距 |
|---|---|---|---|
| 多轮对话第 2+ 轮 TTFT | **~28 ms** | **~1000 ms** | **约 36 倍** |
| 首条冷请求 TTFT | ~1080 ms | ~1260 ms | 同量级(都必须全量 prefill) |

**ON-miss ≈ OFF**(1050-1110 vs 966-1260)——交叉验证通过:随机前缀时开缓存也拿不到收益,
性能差异完全来自"前缀命中",而不是其他变量。

## 5. 两个"实验设计教训"(过程记录)

1. **先用 1.7B 做的预实验看不出差异**(TTFT 全是 ~24ms):小模型在这张卡上 6000 token
   的 prefill 本来只要几十 ms,缓存"省无可省"。→ **性能实验的负载必须让被测环节成为瓶颈**
   (换 8B 后 prefill 变成 ~1000ms,缓存效果才显现)。这也是看基准数据时的通用直觉:
   优化收益的上限 = 该环节占总延迟的比例。
2. **汇总口径第一次用了"所有轮次取中位数",把唯一的冷启动观测淹没掉了**(3 个会话里只有第 1 个
   是冷的,中位数全是热值)。→ 对照实验要先想清楚"冷/热"是两个总体,分开统计。
   (另:脚本 v1 的随机种子不含会话号,第 2/3 个"随机"会话重复了第 1 个的内容导致假命中,
   已修复——随机化要保证真的随机。)

## 6. 结论

- 对**多轮对话/共享上下文**负载,prefix caching 把本机 8B 模型的 TTFT 从 ~1s 降到 ~28ms
  (36x),是交互体验的决定性开关;vLLM V1 默认开启是合理的。
- 对**无重复前缀**负载(如随机 prompt 压测、一次性长文档问答),开启缓存无收益也无明显代价。
- 学习延伸:阅读 `vllm/v1/kv_cache_interface.py` 与 `vllm/v1/core/kv_cache_manager.py`
  可看到块哈希/命中/逐出的完整实现;`vllm bench serve --dataset-name prefix-repetition`
  是官方等价压测入口。
