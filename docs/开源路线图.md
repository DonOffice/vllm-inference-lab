# 开源参与路线图:从 0 到第一个 merged PR,再到 100 star

> 给自己看的行动手册。基于第一性原理 + 对抗性审查写成:每条结论都先问"证据是什么、反面是什么"。

## 1. 第一性原理:作品集到底在证明什么

GitHub 作品集的本质是**降低别人判断你能力的成本**。信号强度排序(从弱到强):

1. 自有仓库但无人问津 → 只证明"会建仓"
2. 小 PR 被 merge(文档/复现类)→ 证明"能读懂大仓流程、沟通专业"
3. 被 merge 的代码 PR → 证明"工程能力被维护者背书"
4. 自有仓库有真实用户(star/issue/PR)→ 证明"能定义并交付有价值的东西"
5. 2-4 的组合 + 持续性 → 这就是我们要的

**所以两条腿缺一不可**:给 vLLM/SGLang 提 PR(借背书)+ 经营自有仓库(攒资产),互相导流(PR 签名档放仓库链接,仓库 README 放"数据被 xx 引用")。

## 2. 对抗性审查:vLLM 是好的第一站吗?

**正面**:我们已经有 3 个实测 PR 候选、完整源码环境、领域知识(见 pr-candidates.md)。

**反面**(必须诚实面对):
- vLLM 是超高频仓库,带 `good first issue` 标签的_issue 常常几小时内被抢_,硬挤这条路挫败感高
- 核心代码 PR 门槛高(内核/分布式),新手直接上的成功率趋近 0
- 但:**文档与代码不一致、实测数据缺失**这类贡献竞争小得多,且我们手里正好有独家实测数据
- SGLang 体量小一档、issue 响应更快,#4133 这种"有 issue 背书的小修复"是比 vLLM 更好的第一滴血

**结论**:vLLM 和 SGLang **都是**好起点,但切入点必须选"我们独有的证据链"而不是抢标签 issue。顺序:SGLang #4133 修复(练全流程)→ vLLM 文档 PR(候选 2,数据最硬)→ vLLM 安装文档(候选 3)。

## 3. PR 完整流程(把每一步讲透)

```
0. 准备(一次性):GitHub 账号 + gh auth login + git config 核对(本机已配 dong/sikaifaker@gmail.com)
1. 找目标:搜 issue(不重复)→ 无人认领 → 评论 "I'd like to work on this"(大仓尤其重要)
2. fork:网页 Fork 按钮,或 gh repo fork vllm-project/vllm --clone
3. 分支:git checkout -b doc/bench-prefix-cache-note   ← 分支名 = 改动内容,一眼可读
4. 改动:最小 diff。文档 PR 也要本地核对引用的命令真能跑
5. 提交:git commit -s -m "..."   ← -s 自动加 Signed-off-by(DCO,法律声明"这代码是我写的")
6. 同步:开发超过几天,先 git fetch upstream && rebase upstream/main(避免冲突被退回)
7. 推送:git push origin doc/xxx  →  GitHub 会弹出"Create Pull Request"
8. PR 描述模板:现象一句话 / 证据(数据表+复现命令) / 改动说明 / 关联 issue(#4133)
9. CI:绿灯不用管,红灯点 Details 看日志,自己先修(最常见:格式 lint)
10. review:维护者提意见 = 好事,当天响应;48 小时无响应可礼貌 ping 一次:"gentle ping, happy to adjust"
11. merge 后:PR 页面会出现在你的 GitHub 贡献图 + 仓库 Contributors
```

**礼仪红线**(违反 = 拉黑风险):不催 merge、不在别人 PR 下刷存在感、不提交未经 issue 沟通的大重构、不用 AI 生成的空话填 PR 描述(维护者一眼看穿)。

## 5. 100 star 剧本(渠道 × 时机 × 话术)

**冷启动三渠道**(按转化率排):
1. **r/LocalLLaMA**(最对口):规则严禁纯链接帖 → 帖子写"踩坑+数据"干货正文,仓库作为"完整数据和交互讲解在这里"。标题示例:"I benchmarked vLLM prefix caching on a 4070 Ti Super: TTFT 1070ms→28ms, and the gotcha that silently corrupts your benchmarks"
2. **V2EX / 知乎 / 即刻**:中文受众,主打"国内网络环境下装 vLLM 的 7 个坑+解法"(痛点型内容天然传播)
3. **dev.to / Show HN**:英文,主打"consumer GPU real numbers"(信息差型:大多数基准是数据中心卡)

**转化优化**(star = 曝光 × 转化,两边都要做):
- README 首屏 15 秒内让人看懂"这有什么、为什么信"(已有:实测表+交互页链接;上线后补一张 GIF)
- 每个渠道帖都附**只有本仓才有的数字**,不写"我整理了一些资料"
- Roadmap 勾选式更新:每次更新都是一次再传播的理由("新增 SGLang 横评"帖)

**对抗性风险清单**(不做这些,做了=慢性自杀):
- ❌ 买 star / 互赞群:GitHub 反作弊会标记,且 star 质量在 pruning 下现形——作品集的要害是可信
- ❌ 搬运他人文章凑数:license 风险 + 一搜就穿
- ❌ 同内容 24 小时内轰炸所有渠道(平台限流,且显得急功近利):间隔 2-3 天、按社区文化改写
- ❌ PR 求星("求个 star 放在 PR 里"):维护者极度反感
- ❌ 数据注水:所有数字保留原始 JSON,被质疑时是最强防御
