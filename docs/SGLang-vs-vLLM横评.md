# SGLang vs vLLM:同一张 4070 Ti Super 上的同日 A/B 横评

> 日期:2026-10-31 · vLLM 0.32.0 · SGLang 0.5.22 · Qwen3-8B-AWQ(两侧同为 awq_marlin INT4 内核)
> **结论先行:稳态性能两者打平(±7% 内);真正的差异在配置悬崖和预热陷阱——本文记录了 benchmark 当天欺骗我两次的全过程。**
> 原始 JSON:WSL `~/bench/results/`(sgl075c*、vllm1031c*)

## 方法学

| 控制项 | 取值 |
|---|---|
| 模型 | 同一份本地 `Qwen3-8B-AWQ`(两侧日志均确认 awq_marlin) |
| 客户端 | 同一个 `vllm bench serve --backend openai`,同机同口径 |
| 负载 | random 1024 in / 256 out,32 请求,并发 1/2/4/8,每档独立 seed(C×17) |
| 预热 | 每侧正式扫描前先跑 8 条小请求(见下文发现 ③) |

| 时间 | 两侧数据同日 1 小时内采集,消除隔天环境差异 |

**解读**:四档吞吐差全部在 ±7% 以内(c=2/4/8 在 ±2% 内),TTFT/TPOT 互有胜负。在单一负载、单一模型、单卡的前提下,**没有赢家**。两个框架的调度器和内核在这张卡上都把带宽利用到了同一水平(c=8 时 ≈426 tok/s,对应 76% 的 8B-AWQ 单流上限推算带宽)。选型应该看别的:模型覆盖、结构化输出、PD 分离、社区生态——而不是这种 benchmark 截图。

## 发现 ①:SGLang 的显存悬崖(0.9 水位 = 崩溃级劣化)

第一次测 SGLang 时我镜像了 vLLM 的 `--mem-fraction-static 0.9`,结果灾难:吞吐 8-30 tok/s、P99 TTFT 高达 **338 秒**、且并发越高越差(c=4 比 c=2 还慢)。服务器日志给出铁证:

```
Capture target prefill CUDA graph end. elapsed=300.44 s, ..., avail mem=0.00 GB
```

SGLang 先按水位划走显存建 KV 池(0.9 → 54513 tokens),**再捕获 prefill CUDA graph 时把剩余显存吃穿到 0**——图捕获爬了 300 秒,运行期零余量,随机多分钟级停摆。降到 0.75 后:图捕获 300s→**11s**,剩余显存 0→**1.84GB**,就绪 370s→**60s**,一切正常。

> vLLM 的 0.9 没事,因为它把 graph/激活预留算进 0.9 里再定 KV 池;SGLang 的水位语义不同。**跨框架搬参数,先查语义。**

## 发现 ②:benchmark 骗了我第一次——旧基线被"冷启动税"压低

10-27 的 vLLM 基线(71.7 / 122.9 / 209.6 / 320.5 tok/s)没有预热,服务就绪后直接开压。同日同参数复测:71.7→**90.6**(+26%)、320.5→**426.4**(+33%)。冷服务器上的首批压测在替 torch.compile / 图捕获 / 时钟爬升买单。**如果我当时直接发"vLLM vs SGLang 隔天对比",会得出"SGLang 快 30%"的错误头条。**

> 三条压测军规(本仓库实测教训全集):① 每档独立 seed 防前缀缓存污染(基线报告 §3);② 正式扫描前先预热;③ 隔天数据不能直接 A/B。
